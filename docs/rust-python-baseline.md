# Bazel Rust and Python baseline

The platform owns the toolchains and their configuration; Bazel is the only build and test orchestrator
([ADR 0025](adr/0025-platform-owned-bazel-configuration.md)). A project selects a pinned release and one of three
profiles and does not choose a compiler, runtime, formatter, linter, type checker or their policy.

| Profile | Languages |
|---|---|
| `rust-bazel-9.3` | Rust |
| `python-bazel-9.3` | Python |
| `rust-python-bazel-9.3` | Rust and Python |

| Component | Version | Where it runs |
|---|---|---|
| Bazel (via Bazelisk 1.30.0, binary digest enforced) | 9.3.1 | host launcher |
| rules_rust | 0.74.0 | Bazel module (source.json pinned) |
| Rust: rustc, rust-std, rustfmt, clippy, rustdoc, rust-src | 1.99.1 | Bazel toolchain, every component archive hash-pinned |
| rust-analyzer, rustc, rustfmt, clippy-driver, rust-src (no Cargo) | 1.99.1 | host, closure-verified (editors, agents) |
| rules_python | 2.4.5 | Bazel module (source.json pinned) |
| CPython (python-build-standalone 20261021) | 3.15.1 | Bazel toolchain and host, the same archive |
| Ruff | 0.17.2 | Bazel (pinned archive) and host, closure-verified |
| pytest, pytest-cov, coverage, mypy | 9.1.1, 7.1.0, 7.17.0, 2.4.0 | Bazel, hash-locked requirements |

Supported hosts: macOS arm64 (`darwin-arm64`) and Linux x86-64 (`linux-x86_64`). A host without a pinned source is
refused by `setup` with the hosts that are supported.

## Adopting a profile

1. Pin the release and select the profile in `dev-platform.toml` (`[platform] profile = "rust-python-bazel-9.3"`).
2. `dev-platform toolchain materialize --pinned --add-hooks` writes the generated files and appends one line to
   `MODULE.bazel` (`include("//dev-platform:toolchains.MODULE.bazel")`) and one to `.bazelrc`
   (`import %workspace%/dev-platform/bazel.bazelrc`); it creates those files and `.bazelversion` only if absent and
   never edits anything else. `--dry-run` shows the plan; without `--add-hooks` the lines are only reported.
3. `bazel mod deps --lockfile_mode=update` produces the project's `MODULE.bazel.lock` (the existing module resolution,
   unchanged). Commit the generated files and the lock.
4. `dev-platform setup` provisions and verifies the host tools; `dev-platform check` verifies the configuration with
   the rest of the environment.

## The contract: the same commands locally and in CI

| What | Command |
|---|---|
| build, unit tests, doc tests, Python tests | `bazel test //...` |
| formatting, lint (Rust: rustfmt, clippy `-D warnings`; Python: ruff check and format, mypy) | `bazel build --config=dp-lint //...` |
| coverage (LCOV, combined) | `bazel coverage //...` |

`dev-platform init` writes these as the checks `bazel.test`, `bazel.lint` and `bazel.coverage` when the configuration
is materialized; `dev-platform check` runs them with `--lockfile_mode=error`.

Rules the platform provides: `dp_py_test` (`//dev-platform:python.bzl`: pytest with the pinned plugins; under
`bazel coverage` it writes LCOV that Bazel merges) and `dp_rust_library` (`//dev-platform:rust.bzl`: the library, its
unit tests, rustdoc and doc tests, edition from the profile). Plain rules_rust and rules_python rules work too; the
lint aspects apply to every `rust_*` and `py_*` target.

## What conformance checks

`dev-platform check`, `toolchain verify` and `setup` add a `bazel-config` item to the environment record. It fails, with
the action that resolves each finding, when:

| Finding | Meaning |
|---|---|
| `missing`, `stale` | a generated file is absent, or edited, or generated by another release: run `toolchain materialize` |
| `foreign` | a file the platform generates exists but the platform did not write it (for example a hand-written `ruff.toml`): it is never overwritten; remove it |
| `unexpected` | a file in `dev-platform/` that this release does not generate |
| `hook` | `MODULE.bazel` or `.bazelrc` does not load the generated files |
| `independent-declaration` | the project declares `rules_rust` or `rules_python`, configures a Rust or Python toolchain, registers one, overrides the rules, or uses another `python_version` |
| `independent-setting` | `.bazelrc` sets a `rules_rust` setting, a Python version or extra toolchains; `.bazeliskrc` pins another Bazel version |
| `tool-config` | `rust-toolchain(.toml)`, `rustfmt.toml`, `clippy.toml`, `ruff.toml`, `mypy.ini`, `pytest.ini`, `.coveragerc`, `.python-version`, `.tool-versions` entries, or `[tool.ruff]`, `[tool.mypy]`, `[tool.pytest]`, `[tool.coverage]` (and the `setup.cfg`/`tox.ini` equivalents) outside the generated files |

Only the languages of the profile are policed. A project's own `pip.parse` at the platform's Python version is not a
conflict.

## Upgrading

Pin the new release, `toolchain materialize` (it updates files generated by an older release and refuses foreign ones),
`bazel mod deps --lockfile_mode=update`, commit. Pinning a release never changes the project by itself.

## Constraints and limitations

- rules_python 2.4.5 ships CPython 3.15.0rc3 for `3.15`. The profile declares the 3.15.1 runtime to Bazel with
  `python.single_version_platform_override` and the same hash-pinned archive the host uses. Bazel's `bazel coverage`
  for plain `py_test` targets reports empty data (the runtime has no coverage tool); use `dp_py_test`.
- rules_rust 0.74.0 does not know the Rust 1.99.1 hashes; the generated module supplies them. Its toolchain repository
  fetches the `cargo` and `llvm-tools` components (pinned; no build, test, lint or doc action here runs Cargo). No Cargo
  binary is installed on the host and no first-party `Cargo.toml` is needed. Crate dependency resolution through Cargo
  (`crate_universe`) is not part of this baseline and is unchanged.
- mypy follows imports silently (`follow_imports = silent`): each first-party target is checked on its own; code of
  third-party packages is not checked and needs its type information to be importable from the target's dependencies.
- Python dependencies of the project itself keep using the project's own `pip.parse` and lock; the platform's hub
  (`dp_pytools`) only carries the test, coverage and type-checking tools.
- Conformance proves the files, the hashes and the absence of conflicting settings. It does not prove Bazel's
  repository cache, the host C toolchain or the network at fetch time.
- Windows is not supported.

## Authoring a new baseline

`python3 tools/admit_baseline.py` prints the profiles for the candidate versions from the publishers' own checksums
(Rust channel manifest, python-build-standalone `SHA256SUMS`, ruff and Bazel checksum files, Bazel Central Registry) and
`--write` updates `toolchains/manifest.json`. Closure digests of executed tools are measured on each platform
(`toolchain measure`) and passed back with `--closures`. The Python requirements are re-locked with
`uv pip compile src/dev_platform/bazel/python_tools.in --universal --python-version 3.15 --generate-hashes --no-build`.
