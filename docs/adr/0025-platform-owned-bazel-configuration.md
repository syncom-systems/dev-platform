# 0025 Platform-owned Bazel configuration

Status: Proposed (owner directive, 2026-10-23: the platform is the single authority for development toolchains and
their configuration; Bazel is the sole build and test orchestrator).

## Context
A project selects a pinned platform release and a toolchain profile. Until now a Bazel profile only *reconciled* what the
project declared: the project's `MODULE.bazel` named the Rust version and the rules, and the platform checked the names
against its manifest. Compiler options, formatter and lint policy, the Python runtime, the type checker and the test and
coverage tooling were each the project's own, so two projects on the same release could differ in everything but the
version string, and an editor, an agent and CI could each see a different policy.

## Decision
1. **A profile can own the Bazel configuration.** A manifest profile with a `bazel` section (`edition` for Rust) and
   Bazel-managed `rust-toolchain` and/or `python-runtime` tools is rendered by `src/dev_platform/bazelconf.py` into the
   files Bazel and its language rules need. Every version, url and hash in the rendering comes from the manifest (one
   pin, two uses: the host tool and the Bazel declaration); the policy (rustfmt, clippy, ruff, mypy, coverage, test and
   lint rules) is static files of the release under `src/dev_platform/bazel/`, so it is covered by the release's tree
   digest, SBOM and provenance.
2. **Materialization is explicit and never overwrites.** `dev-platform toolchain materialize` writes the files. A file
   the platform did not generate is refused (nothing is written); a file it generated is updated; project-owned files
   are never edited, except that `--add-hooks` appends the two entry lines (`include(...)` in `MODULE.bazel`, `import` in
   `.bazelrc`). The generated files are committed by the project like any other file and carry their origin
   (`# generated by dev-platform <release> for profile <profile>`).
3. **Conformance fails on conflicts, with the action that resolves each.** `verify_profile` adds a `bazel-config` item to
   the environment record: the project's files must equal the release's rendering, the entry lines must be present, and
   independently maintained settings that the platform owns must be absent: a second `rules_rust`/`rules_python` or
   toolchain declaration, a Rust or Python version chosen elsewhere (`rust-toolchain.toml`, `.python-version`,
   `.tool-versions`, `USE_BAZEL_VERSION`, flags in `.bazelrc`), and formatter, linter, type-checker, pytest or coverage
   configuration (`rustfmt.toml`, `ruff.toml`, `mypy.ini`, `[tool.ruff]`, ...) that is not the generated one. The
   Python tools (`pytest`, `pytest-cov`, `coverage`, `mypy`) are Bazel-managed tools `bound_to` that item: their identity
   is `config-locked` (the hash-locked file that declares them is proven equal to the release's), never stronger than
   what the check established.
4. **Bazel remains the only orchestrator.** Formatting, lint, type checks, tests, documentation checks and coverage run
   as Bazel actions (`bazel test //...`, `bazel build --config=dp-lint //...`, `bazel coverage //...`) with rules_rust
   aspects and platform-owned Starlark (`dp_py_test`, a Python lint aspect, `dp_rust_library`). The host toolchain the
   platform provisions (Rust without Cargo, CPython, ruff, Bazelisk) is for editors, agents and the platform's own
   commands, and is the same bytes Bazel is told to fetch.
5. **Version constraints are reported, not worked around.** rules_python 2.4.5 knows CPython 3.15.0rc3 as `3.15`; the
   profile therefore declares the 3.15.1 runtime to Bazel with `python.single_version_platform_override` using the same
   python-build-standalone archive and hash the host tool uses. rules_rust 0.74.0 has no built-in hashes for 1.99.1 and
   would download its components unverified; the rendering supplies `sha256s` for every component archive.

## Consequences
- Existing releases, profiles and consumers are unchanged: the new profiles are additive and no existing profile has a
  `bazel` section.
- Bumping the pinned release is: `toolchain materialize`, `bazel mod deps --lockfile_mode=update`, commit. The module
  lock file stays the project's, produced by the existing machinery, which this decision does not change.
- Cargo: no Cargo interface is installed on the host (`cargo`, `cargo-clippy` and `cargo-fmt` are not), and no first-party
  `Cargo.toml` is required. rules_rust's toolchain repository still downloads the `cargo` and `llvm-tools` components
  (pinned, not invoked by any build, test or lint action here); crate dependency resolution through Cargo
  (`crate_universe`) is outside this decision and unchanged.
- The conflict scan is a text scan of the project tree for the settings listed in 3; it is not a Bazel analysis.
